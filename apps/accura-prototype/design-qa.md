## Findings

No actionable P0, P1, or P2 differences remain in the redesigned Documents flow. The unresolved role matrix, External Document lifecycle, taxonomy conflicts, and production e-signature rules remain product-verification gaps rather than hidden implementation assumptions.

The implementation now intentionally differs from the older Accura demo and the preceding neutral pass in these ways:

- Zinc 100 (`#F4F4F5`) forms a continuous true-neutral application shell and document canvas. The former full-page white workspace has been removed.
- The sidebar uses Brand 950 (`#00393F`) as its surface with Zinc 200 content. Selected and hovered navigation use Zinc 100 with Zinc 900 icon and label.
- Filter controls, result count, title, description, primary action, and pagination sit directly on Zinc. The sticky top bar and table are the two white, rounded, bordered surfaces.
- Mint is limited to the table header and subtle table hover states; coral remains limited to the unread badge.
- The official Accura SVG lockup and mark replace the generated raster placeholder.
- The sidebar collapses from 248 px to exactly 64 px. In the collapsed state the standalone mark remains the sole visual and acts as the expand control.
- The notification count has its own ring and visible overflow, so it no longer clips into the bell control or header edge.
- The old section label in the top bar is replaced by a functional global search with a visible `⌘ K` shortcut.
- All product-interface icons now use Iconoir on a consistent 24 × 24 grid and 1.5 px stroke; the Accura logo remains the supplied brand SVG.
- The Document list now opens status-aware record screens directly; secondary row actions retain the quick-view dialog.
- Create/Edit uses a sectioned Record Editor with readiness, uploads, metadata, references, routing, and sticky Draft/Submit actions.
- Review, QA Approval, and Approved use one Record Detail shell with a dominant preview, workflow stepper, metadata rail, signature chain, role-aware decisions, and Audit Trail drawer.
- Dashboard combines the existing Accura overview and action-record structure with the supplied mint quality-workspace illustration. The banner keeps the requested eyebrow and headline in the open left region while the remaining workspace stays Zinc with white cards.
- Dashboard navigation is now functional. Dashboard and Documents share the same shell, selected navigation treatment, global search, notification, and profile controls.
- Dashboard module cards use restrained semantic color plus a branded selected state; Records retains the existing Accura tabs, priority filter, statuses, due dates, and realistic action data.

## Comparison History

### Iteration 53 – The Settings module's three unbuilt stories, and the values they finally own

Built `US-007 - Manage Document Types`, `US-008 - Configure Record Numbering` and `US-009 - Manage Departments` (all PRD-001), which were the last three unbuilt stories in that PRD.

- **Settings > Organisation was telling the user the requirements did not exist.** The section read *"No PRD or user story covers this section, so nothing is built here yet."* That was true when it was written, and false from the moment the 2026-11-10 sync added `US-008` and `US-009` — both of which name `Settings > Organisation` as their entry point. A sentence in the product asserting a requirement does not exist is worse than a backlog item, because nobody reads it as a gap.
- **`US-007`: the table was missing half the story.** It had Name, Abbreviation, Description, a search and a count; AC-01 also wants the **Periodic Review Frequency**, AC-05 a row **Edit**, AC-03 an **Add Type** form. All built. Validation measured against AC-04: a duplicate abbreviation entered as `br` against the existing `BR` is refused (compared case-insensitively, saved uppercase), and a frequency of `0` is refused as "a whole number of years, 1 or more". A valid save adds the row — measured `Standard Operating Procedure · SOP · — · 4 years`, with the em dash for the blank description.
- **`US-008`: the preview is generated the same way an ID is.** One function, `formatDocumentId`, serves both, so the preview cannot drift from what the modules produce. Measured AC-02: switching the separator to a slash moved the preview from `ACME-BR-2026-000001` to `ACME/BR/2026/000001`; AC-03: an empty prefix is refused with "Enter an organisation prefix."
- **`US-009`: departments with the duplicate rule AC-03 spells out** — names differing only in case are the same name. Blank descriptions show an em dash, per AC-01.

**What makes these three worth building together is what they configure.** Each had a hard-coded twin in the module that needed it: the review frequency as `DEFAULT_REVIEW_YEARS = 3` in the document details, the numbering as literals in the create form, the departments as an array in `document-directory.ts`. Settings showed values it did not own, and the modules used values nobody could change. They now live in `components/organisation-settings.ts`, the state sits in `DocumentsPrototype`, and both sides read it.

Measured end to end, without a reload:

| Change in Settings | Effect in Documents |
|---|---|
| Record (REC) frequency 3 → 7 years | `ACME-FRM-2026-000006` Next periodic review moved **29 Sep 2029 → 29 Sep 2033** |

| Prefix `ACME` → `QMS`, separator → `/` | A document created after saving took the ID **`QMS/BR/2026/000012`** |

- `document-directory.ts` kept only the people roster; its department list is deleted rather than left as a second copy, which is the drift that module exists to prevent.
- A stale bundle sent me chasing a phantom: clicking Settings did nothing and no error appeared in the console. The code was right — the dev server was serving the pre-refactor page. The Tailwind/HMR trap recorded on 2026-11-10 applies to component changes too, not only to new utility classes.

- **The register's department filter now reads Settings too.** It had derived its options from the sample rows, so a department added in Settings never appeared until some document already used it, and a renamed one kept its old name. Measured: adding **Quality Assurance** in Settings puts it in the filter immediately, with no document using it.
- **"Save Record Numbering" became "Save", disabled until something in the section changes.** The heading above it already says Record Numbering, so the label was repeating its own context; and a Save that is always pressable tells the reader nothing about whether there is anything to save. Measured: disabled at rest → enabled after editing the prefix → disabled again after saving.
- **A sentence-case sweep over every button and menu item.** Six were Title Case against the rest: *Add User*, *Add Type*, *Add Attachment*, *Save as Draft*, *Submit for Review*, *Acknowledge & Register* — the last three especially, because the Draft editor already said *Save as draft* and *Submit for review*, so the same two actions were spelled two ways on two screens. ### Iteration 50 – One coloured mark per card

Iteration 49 fixed the *meaning* of the dashboard card's colour and not the *amount* of it. The user's reply — "nhìn vẫn bị dơ do trông nhiều màu quá" — was right, and the measurement says why.

- **Each card was carrying three coloured marks for one fact.** A state-coloured rule across the top, a state-tinted icon, and a state-tinted badge — all saying "Overdue". Five cards × three marks is fifteen pieces of colour for five numbers. Giving the stripe a meaning made it defensible; it did not make it necessary.
- **The rule is gone, the icon is neutral, and the badge is the only colour.** The badge already says the state in words, so it is the one mark that cannot be removed without losing information. The icon takes the brand's soft surface with a teal glyph, the same on every card.
- **Radius 20px**, up from 12.
- **The odd border on Documents was a selection state that selected nothing.** `selectedModule` was written and read in exactly one place: its own styling. It filtered no list and changed no other content — it just gave one card a brand border and a ring on load, which is what the user spotted. Deleted.
- **Only Documents is a button now.** It is the only module built, so it was the only card whose click did anything once the dead selection state went; the other four were buttons that lifted on hover and led nowhere. They are plain cards. A control that looks pressable and does nothing is worse than one that does not look pressable.
- Measured across all five: `border-radius: 20px`, one border colour `oklab(0 0 0 / 0.08)`, no ring, no rule — on every card, with one `<button>` among four `<div>`s.

### Iteration 49 – The dashboard cards stop decorating and start reporting

Reworked against a reference the user supplied (a Ferndesk reporting overview), in Accura's own palette rather than the reference's.

> **Partly superseded the same day by Iteration 50.** The state-coloured rule described below was removed: making the stripe mean something was not enough, because the card still carried three coloured marks for one fact.

- **The top rule was a lime smear.** `--accura-pop` (`#d9f25f`) sat across every card at 72% opacity — the same on all five, regardless of state. Grepping it found the colour is used in **exactly one place in the whole prototype**, which is why it read as dirt rather than as part of the system: nothing else on any screen ever repeats it. The rule now carries the **state** — emerald for On track, amber for Due soon, red for Overdue — which is the one thing a reader scanning five modules is actually looking for.
- **Selection and state had been fighting over the same stripe.** Selecting a card turned its rule brand-green *and* filled its icon *and* added a ring: three mechanisms for one bit, and a selected Overdue card lost the fact that it was overdue. Selection is now the ring and border alone; the rule is always the state.
- **The badges were the only saturated red in the product.** `destructive` is solid red on white; every other status in Accura uses the 8% tint (`error`, `warning`, `success`). Three solid red chips in a row shouted over the numbers they were labelling. Measured after: `oklab(… / 0.08)` surfaces with red-700, amber-700 and emerald-700 text — the same treatment as the register's status column.
- **The number now owns a line.** It had shared one with the detail sentence, so the figure the card exists to show competed with a line of grey text. It is `text-3xl` tabular on its own line, the module name under it, the detail muted beneath — the reference's order, which puts the value first.

- **The gap is deliberate, and settled.** Five modules in a three-column grid leave a hole in the second row. A five-column row fits at `xl` but truncates captions like "due within 14 days · of 13 open" — tidying the layout at the cost of the data is the wrong trade. ### Iteration 48 – Approving asks first, and the shell says who you are

- **Approving had nothing in front of it.** The signature step was removed on 2026-11-10 as built-ahead-of-requirement, and nothing replaced it — so one click recorded an auditable decision. Rejection kept a dialog because a reason is mandatory; approval, the more consequential of the two, kept none. It now confirms, naming the document, the person it will be recorded against, and the consequence. ### Iteration 38 – The action belongs to the hovered row, and it is a raised chip

- **The raised cell was on every row at once.** Iteration 37 tied it to the table's scroll state alone, so the moment the register had anything left to scroll, all ten rows lifted their trailing cell together — a permanent grey band down the right edge, sitting on top of the Author column and making it unreadable on every row at once. A raised surface should say "this row, now", and it was saying nothing.

- **The elevation moved off the cell and onto the action.** Iteration 37 put a 1 px edge and a left-cast shadow on the cell itself, and at the cell's own size against a near-white row it was present in computed style but invisible in use — twice now. The action is a raised chip instead: white, a 1 px border, a 10 px radius and a three-layer shadow (`0 1px 2px / 8%`, `0 4px 10px -2px / 16%`, `0 12px 24px -8px / 28%`). A bordered white chip on the row's Zinc 50 hover surface separates on contrast, not on shadow alone, so it survives being looked at on a laptop screen.
- **The cell now only masks.** On the hovered or focused row it takes the row's Zinc 50 hover surface so the columns passing underneath do not show through, and carries no border and no shadow of its own — measured `border-left-width: 0px`, `box-shadow: none`.
- **The header's trailing cell is no longer sticky at all.** It had stayed pinned and opaque, so it clipped "Document type" to "Docu…" and read as a grey block in the corner of the header while the body rows beneath it were clean. A header is never hovered and holds no action, so it has nothing to pin for: it now scrolls with its own row like every other heading. Measured `position: static`, `background-color: rgba(0, 0, 0, 0)`.
- **Hover alone would have been a regression.** A hover-only control is unreachable by keyboard and on touch, so the chip answers to `:focus-within` on the row as well, and stays visible while its menu is open. Verified by focusing the row's action button with the pointer parked away from the table.
- **The open menu took the row away with it.** The menu popup is portalled out of the table, so the moment it opened the pointer had left the row and focus sat inside the portal: `:hover` and `:focus-within` were both false, the masking cell went transparent and the chip went to `opacity: 0`. What was left on screen was a ghost of the trigger over the Author text scrolling underneath it, with a menu hanging off nothing. Reported from the running prototype.
- **The open row is now state, not a CSS state.** `openMenuRow` holds the key of the row whose menu is open, set from the menu's `onOpenChange`; the row, its masking cell and its chip each take their revealed class from it. Driving it off the trigger's `aria-expanded` instead would not have helped: the cell and the row are not the trigger, and nothing in CSS relates them to a portalled popup.
- Measured with the menu open and the pointer away from the table: row `:hover` false, `:focus-within` false, and still cell `rgb(250, 250, 250)`, chip `opacity: 1`, white, 1 px border, 10 px radius, three shadow layers — while every other row stayed at `rgba(0, 0, 0, 0)` and `opacity: 0`.
- **Two chips at once, and only one row hovered.** `:focus-within` was the cause: closing a menu returns focus to its trigger, so that row stayed revealed while the pointer had already moved to another — two raised chips, one of them on a row the user was not pointing at and had stopped interacting with. The reveal now answers to `:focus-visible` (`group-has-[:focus-visible]`), which a mouse click does not set, so a mouse-driven close leaves no chip behind while a tabbed-to row still shows one.
- Measured after clicking a trigger, closing the menu and hovering a different row: exactly one chip, on the hovered row, with the former row back at `opacity: 0`. Tabbing into the table with the pointer off it reveals exactly the focused row.
- While a menu is open and the pointer is on another row, both rows show a chip. That is intended — the open menu has to keep its own row marked, or it hangs off nothing.
- **At the end of the row the chip stops being a chip.** Once the register is scrolled to its end, the actions sit in their own column straight after Effective date with nothing behind them, so there is nothing to lift off and nothing to cover. Every row shows a plain action — no surface, no border, no shadow, and the cell behind it transparent — and the column reads as the register's last column rather than as something floating over it. Measured at the end across all ten rows: `opacity: 1`, `border-width: 0px`, `box-shadow: none`, chip and cell both `rgba(0, 0, 0, 0)`.
- **And every row shows it, not just the hovered one.** Revealing one row at a time earns its keep only while the action is covering a column; in its own column it is just a column, and hiding nine of ten actions would make the register look broken.
- Scrolled back off the end, the same rows return to one raised chip on the hovered row — measured `opacity: 0` on all ten with the pointer away, and the chip's white surface, 1 px border and three shadow layers intact.
- `atEnd` therefore has to reach the rows: `ScrollableTable` now takes a render function and hands its own scroll state down, rather than publishing it as a `data-` attribute for CSS to read. The attribute stays for inspection.
